# Архитектура системы

## Схема целиком

```
                    ┌─────────────────────────────────────────┐
                    │  VPS "vpnmain" (57.129.40.28)            │
                    │  Ubuntu 24.04, Docker, Caddy              │
                    │                                           │
  Владелец          │  ┌──────────────┐   ┌──────────────────┐ │
  ресторана  ──────▶│  │   Directus   │   │  build-webhook   │ │
  (браузер)         │  │  + Postgres  │   │  контейнер       │ │
                    │  │  (CMS)       │──▶│  (Node, Astro,   │ │
                    │  └──────────────┘   │   Wrangler)      │ │
                    │   panel.veloce-      └────────┬─────────┘ │
                    │   network.xyz/admin           │           │
                    └────────────────────────────────┼───────────┘
                                                       │ wrangler pages deploy
                                                       ▼
                                          ┌────────────────────────┐
                                          │   Cloudflare Pages      │
                                          │  (по проекту на клиента)│
                                          └────────────┬────────────┘
                                                        │
                                                        ▼
                                          Посетитель сайта ресторана
                                          (<slug>.pages.dev или
                                           кастомный домен клиента)
```

## Поток данных при правке контента

1. Владелец ресторана логинится в Directus (`panel.veloce-network.xyz/
   admin`), меняет цену/фото/текст — видит только свой ресторан
   (изоляция на уровне прав, см. [directus-cms.md](./directus-cms.md))
2. Directus **Flow** (event hook на `items.create`/`items.update`)
   резолвит `restaurant_id` и дёргает `POST /webhook/build` с секретом
3. `build-webhook` контейнер: читает ресторан по id/slug из Directus
   (публичное API, без токена, только для `status=published`), если
   published — гоняет `astro build` с `RESTAURANT_SLUG=<slug>`, затем
   `wrangler pages deploy` в Cloudflare Pages проект с тем же именем
4. Через ~10-20 секунд изменения живые на сайте

Подробности и грабли — [automation-pipeline.md](./automation-pipeline.md).

## Почему так разделено

- **CMS на своём VPS** — полный контроль над мультитенантной моделью
  данных и правами, ноль подписки на SaaS
- **Сами сайты — на Cloudflare Pages, не на VPS** — если VPS ляжет
  (обновление, атака, диск), у клиентов сайты продолжают работать.
  VPS отвечает только за возможность *редактировать* контент, не за
  раздачу самого сайта
- **Один Astro-шаблон, много деплоев** — код не форкается на клиента,
  различие только в данных (через `RESTAURANT_SLUG` на этапе сборки) и
  визуальных настройках (цвета/лого хранятся в самих данных ресторана)

## Компоненты и где что живёт

| Компонент | Где | Технология |
|---|---|---|
| CMS + БД | VPS, `~/directus-cms/` | Directus 11 + Postgres 16, Docker Compose |
| Билд/деплой сервис | VPS, `~/deploy/` | Node 22 контейнер, кастомный HTTP-сервер |
| Reverse proxy | VPS, системный | Caddy (уже стоял, шарится с VPN-сервисом) |
| Astro-шаблон (исходники) | Локальная машина, `~/Documents/websites/restaurant-template` | Astro 7 + Tailwind v4 + TS |
| Живые сайты клиентов | Cloudflare Pages, 1 проект на клиента | статический билд Astro |
| Ops-скрипты | VPS, `~/scripts/` | Python (онбординг), bash (бэкапы) |

## Важное ограничение окружения

VPS **не выделенный** под этот проект — на нём же крутится VPN-нода
(Pasarguard) и торговый бот (Polymarket). Решили оставить всё на одном
сервере (осознанный выбор владельца — см. обсуждение в истории),
разделив риски тем, что клиентские сайты не зависят от аптайма этого
VPS напрямую (только CMS/редактирование зависит).
